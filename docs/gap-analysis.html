Gap analysis — what is still missing

<strong>Date: 11 November 2026, 21:00 CET. Updated 12 November 2026, 15:30 CET.</strong> The specification (spec-en.md) has <strong>77 distinct numbered requirements</strong> (87 lines if the grouped ranges are counted line by line). This file listed <strong>100 concrete gaps</strong>: the requirement lines that are not fully satisfied, and everything else a submission is judged on that is not a requirement line.

<strong>41 of those 100 are closed</strong> and are marked inline (Closed 11-12/11 for the night wave that delivered the reference servers, the publication pipeline, the quality gates, the QNX 7.1 guest in CI and the submission pack; Closed 12/11 for the wave that delivered the faulty server, the directed cases of §7.4, the vhost-user front end driving the real virtiofsd, the shared configuration file, the Debian skeleton and the devcontainer). Rows are kept rather than deleted: the closure note says <em>what</em> closed them, so a claim can be checked. What is left: 28 requirement gaps (24 of them blocked on the QNX SDP, 2 de-scoped X-tier, 2 doable here), and 31 non-requirement gaps.

Where the 77 requirements stand:

State Count Meaning
Green 50 implemented <strong>and</strong> covered by an automated test that runs here
Partial 21 the code exists, only one side of the claim is proven
Not started 6 the design is decided, the work is not done

Legend: <strong>[S]</strong> = needs the QNX SDP, blocked on a myQNX account · <strong>[P]</strong> = doable here, now · <strong>[X]</strong> = extreme tier of the specification, de-scoped on purpose.
