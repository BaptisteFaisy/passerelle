What did not work

Five things cost real time, and four of them changed a design or a process. They are written down because a submission that only lists what worked is not a submission anybody can build on. Each entry says what was tried, what actually happened, what it cost, and where the fix lives.

1. The QNX SDP could not be obtained without an account

<strong>Tried.</strong> Install QNX SDP 8.0 (QNX Everywhere) to cross-compile the driver with qcc and to build a guest image with mkqnximage, as the specification assumes (§4.3). Every route was checked on the development machine: no qcc, no mkqnximage, no ~/qnx800, and no public download that does not require a myQNX account. The community image that is known to ship an SDP, ghcr.io/kodebooth/qnx-sdp, is <strong>private</strong>.

<strong>What happened.</strong> Nothing to install. The machine has QEMU 8.2.2 and virtiofsd, so the <em>host</em> half of the project is fully exercisable, and the <em>guest</em> half is not.

<strong>What it cost.</strong> This is the single blocking item of the project: feasibility tests <strong>E1 (driver half), E2, E3 and E4</strong> cannot be run; <strong>PERF-02 … PERF-07</strong> have no measurement; <strong>21 requirements stay partial</strong> and the QNX driver sources have never executed. It also means the demonstration video cannot show a QNX guest mounting the share, which is the shot the whole project was designed around.

<strong>What we did instead.</strong> Rather than assert that the driver works:

  • layers 1 to 3 were made portable C11 with no OS header, so they are built, tested and fuzzed on the PC in CI (P9-10 is a requirement, and it is now the reason the project has any proof at all);
  • a **mock virtio backend** (`virtio/src/mock.c`) replaced the missing device, so the transport is tested without QNX;
  • the QNX-only files are compile-checked against stub headers (`tests/qnx-stub/include`, CI job `qnx-syntax`) — which proves they parse and type-check, and is labelled as such everywhere;
  • a **real QNX 7.1 guest** was booted to ask the device what it looks like from the QNX side (next entry).

Recorded in 0 §3 and §4, and in 1 (every gap marked [S]).

2. The QNX 7.1 image we could get ships no compiler — and routes no interrupt

<strong>Tried.</strong> Use the community QNX Neutrino <strong>7.1.0</strong> x86_64 image (2022-07-12) as the guest: build our driver into it, mount the share, run a binary from it.

<strong>What happened.</strong> The image boots fine under QEMU 8.2.2 and its own tools answer, but it is a <em>runtime</em> image: <strong>no qcc, no mkifs</strong>. It cannot build our driver and nothing can be compiled for it. It is also 7.1, not 8.0, so the kernel changes the design relies on (InterruptAttach() removed, the capability model) are not exercised by it.

One more thing came out of it, and it is a finding rather than a failure: pci-tool -vv reports our device as 1af4/1009 with the MSI-X capability, the five virtio vendor capabilities and three assigned BARs — <strong>and Interrupt list - 0 assigned</strong>. The image's pci_hw.cfg routes INTx only for other bus/device addresses, and pci_server.cfg sets DO_BUS_CONFIG=no, so the BARs are assigned by QEMU firmware, not by the PCI server. A driver must therefore add its own INTx entry (bus, device, pin A) or take the MSI-X path, for which the image does ship pci_cap-0x11.so.

<strong>What it cost.</strong> E1 stays half answered; FS-06 (execute a binary from the share), QNX-02, QNX-06 and QNX-07 cannot be demonstrated.

<strong>What we kept.</strong> The observation is now evidence instead of an assumption: 0, with the transcript copied from the guest, and the interrupt-routing consequence is written into the driver design and into ADR-003's PCI id discussion. It also cross-checks our device-id constants against a real QEMU rather than against a datasheet (VIO-01, VFS-01).

3. The lookup / getattr symlink convention was inverted

<strong>Tried.</strong> Implement the backend interface with lookup and getattr as two attribute calls, without writing down which one follows a final symbolic link.

<strong>What happened.</strong> rmfs assumed one convention, the POSIX truth backend and the 9P adapter assumed the other. The observable symptom was inverted: lstat on a link loop answered <strong>ELOOP</strong> while stat on the same path answered <strong>OK</strong>. Worse, because the walk never <em>saw</em> a link, it never produced the redirect answer QNX needs, and <strong>FS-08 (loop detection) was unreachable</strong> — every lstat on a symlink was wrong.

<strong>What it cost.</strong> A conformance defect that no amount of reading would have found: it was the differential bench (tests/e2e) that produced it, on a randomly generated symlink loop.

<strong>Fix.</strong> The convention is now written where both sides read it, in 0: lookup = lstat(2) semantics, never follows the final link; getattr = stat(2) semantics, follows it and may legitimately return ELOOP or ENOENT. An adapter whose protocol cannot distinguish the two may implement both identically, because rmfs resolves links itself through readlink. Pinned by test_rmfs_path (test_symlink_yields_redirect, test_symlink_loop_detected, test_open_nofollow_refuses_symlink). Full record: ADR-001.

4. strict: true on branch protection is incompatible with the Mergify queue

<strong>Tried.</strong> Protect main the conventional way: required status checks <strong>and</strong> "Require branches to be up to date before merging" (required_status_checks.strict: true).

<strong>What happened.</strong> Measured on pull request <strong>#13</strong>: with every check green, the Mergify queue <strong>refused to queue anything</strong> and posted a failing Mergify Merge Queue check reading <em>"Configuration not compatible with a branch protection setting"</em>. The mechanism is structural — the queue tests a PR through a draft built on the latest base and then merges the <em>original</em> branch, which GitHub by then considers out of date. Two extra traps on the same afternoon: the protection endpoint is PUT (a PATCH answers 404), and all four keys must be supplied or GitHub answers 422. And queue_rules alone does nothing: a pull_request_rules entry with a queue action is required, plus the Merge Queue product activated for the repository.

<strong>What it cost.</strong> Roughly a day of CI archaeology, and a merge pipeline that silently did nothing while looking configured.

<strong>Fix.</strong> strict: false, every required context kept, and the reasoning written down with the exact gh api call: ADR-005 and 2. Losing strict costs nothing here because the queue re-tests every PR on the latest base together with the ones ahead of it, and hermes-lite watches freshness separately (in dry-run: it alerts, it never merges). If strict ever has to come back, the queue must switch to merge_method: fast-forward or to serial in-place checks.

5. -trace file= writes a binary trace, not text

<strong>Tried.</strong> Record the QEMU 9P trace for the round-trip baseline with -trace 'enable=v9fs_*' -trace file=baseline.log, then parse baseline.log as text — the whole benchmark (host/bench/trace.py) counts one line per event.

<strong>What happened.</strong> The file was <strong>simpletrace binary</strong>, not text: the parser found no v9fs_* line at all. On Ubuntu's QEMU 8.2 the trace events go through the log backend, which writes plain text to the file named by <strong>-D</strong>; the file= option belongs to the simpletrace format.

<strong>What it cost.</strong> A baseline that looked recorded and contained nothing usable — the failure was loud (no 9P event in <file>; start QEMU with -trace 'enable=v9fs_*' -trace file=...), but the message itself pointed at the wrong option, which cost another round.

<strong>Fix.</strong> qshare passes both switches — -D <path> for the text log the parser reads and -trace enable=v9fs_* to enable the events (3, with the reason in a comment), and the error message in 4 names the working combination. A second limit is stated rather than papered over: the text log carries <strong>no timestamps</strong>, so latencies are not reported at all — round trips per call do not need them (ADR-004).
