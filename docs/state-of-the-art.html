State of the Art

This document extends Section 2 of the specification with <strong>code-level verification</strong> of the three existing public projects, performed on 10–11 November 2026 by reading the repositories vendored read-only for this study.

<strong>Honesty rule (spec Section 14).</strong> For every fact below we state its source: <strong>[code]</strong> = read directly in the project's source files (file paths given); <strong>[docs]</strong> = read only in the project's documentation, not verified by execution; <strong>[unverified]</strong> = claimed by us but not yet confirmed. <strong>None of the three projects has been executed</strong> — the host PC has no QNX SDP.

2. What We Read in the Code vs Only in the Documentation

Read in the code (paths are inside the vendored copies)

  • **A**: `lib9p/include/lib9p/p9.h` (full 9P2000.L message enum incl. `Tsymlink=16`, `Tstatfs=8`), `src/errno_map.c` (Linux→QNX errno table with explicit switch, `EIO` fallback), `src/transport_virtio.c` (mmio-only backend), `LICENSE` (Apache-2.0).
  • **B**: `include/protocol/nine_p_types.h` (exact 13-message subset), `src/transport/pci_transport.cpp` (manual MSI-X programming with INTx fallback; device ID 0x1009 per README), `src/resmgr/fs_virtio9p.cpp` (resmgr/iofunc integration), Eclipse Apache-2.0 headers.
  • **C**: `src/virtio/virtio.c` (`InterruptAttachThread` IST loop, spinlocks, polled device reset), `src/virtio/virtq.h/.c` (descriptor allocation/chaining API, no indirect descriptors, no EVENT_IDX feature negotiation), `src/virtio_pci/virtio_pci.c` (modern-only PCI IDs `0x1040+type`, full `libpci` MSI-X sequence, capability parsing incl. `SHARED_MEMORY_CFG=8`), `src/virtio_mmio/virtio_mmio.c` (v1 and v2 register maps incl. per-queue reset), `tests/gpio/` (QEMU/serial integration tests), `cmake/toolchains/` (x86_64 + aarch64le), `LICENSE.md` (MIT).

Read only in documentation (not verified by execution)

  • **A**: all functional claims (exec-from-share, symlink behavior, timeout recovery, cache semantics, ability set); its "gaps" list in the user guide was **not read**.
  • **B**: claimed PCI auto-discovery details beyond what the code inspection showed; performance characteristics; ARM64 MMIO base addresses (`smem=0xa003600,irq=75` in README examples).
  • **C**: README build/test workflow; the claim that the library is reusable "for other virtio drivers".
  • **All three**: runtime behavior under QEMU. Nothing was executed — feasibility tests E1–E5 cover this (see [verification-status.md](verification-status.md)).

3. Gaps Passerelle Fills

Gap (spec Section 2) Evidence from this study
<strong>Complete share on x86_64 guest</strong> A has no PCI backend in code; B's x86_64 client implements only 13 of the ~25 messages needed for POSIX parity (no setattr, symlink, fsync, statfs)
<strong>virtiofs for a QNX guest</strong> None of A/B/C contains any FUSE protocol code; QNX Hypervisor's virtio-fs is host-side only <strong>[docs: QNX hypervisor page, spec §2]</strong>
<strong>Conformance + benchmark testbed applicable to all clients</strong> A tests against server traces; B has none documented; C tests only its GPIO sample — none provides a differential harness runnable against a third-party client
<strong>Priority-ordered request scheduling</strong> No priority logic found in A/B/C code; C uses a plain spinlock-serialized queue
<strong>One-command setup on mkqnximage images</strong> A requires manual snippet + QEMU flags <strong>[docs: README quickstart]</strong>; B is embedded in a Bazel runner; C has no host tooling
<strong>PC-buildable, fuzz-testable protocol layers (P9-10)</strong> None of the three builds without the QNX SDP (A: SDP required; B: Bazel+SDP; C: <sys/neutrino.h> in core transport)

4. Other Observations

  • **QNX Hypervisor virtio-fs**: QNX documents a virtio-fs *device* where QNX is the **host** sharing folders with Linux/Android guests **[docs: spec §16 link]**. No guest-side QNX virtiofs driver was found; absence remains **unproven** — the question will be asked on the hackathon Discord (spec §11, §14).
  • **Reuse posture**: per [decisions.md](decisions.md), Passerelle writes its own transport (D3) and offers the PCI/x86_64 work back to project A (D2). No file is copied from any of the three repositories; see [NOTICE](../NOTICE).
